# RushLink 0.1.3 early alpha — for HeadRush firmware 5.2.0

**Target firmware: HeadRush 5.2.0. App version: RushLink 0.1.3.**
This release focuses on firmware 5.2.0 and its multiple-NAM controls. Live API
investigation used a Flex Prime running `5.2.0.2a405ee`; Prime and Core have not
been independently verified on hardware. Capability checks retain the older
single-NAM path for devices running 5.1.

## Multiple NAMs in rigs and Test Rig Studio

- Add a second independent NAM block to the standard processing chain when the
  connected device exposes it. Each host has its own capture files and controls.
- Add additional NAM blocks to Test Rigs and choose the audition host and chain
  slot. Auditioning replaces that host's primary capture and preserves the other
  configured captures.
- Prefer NAM2 / A2 Full, NAM2 / A2 Lite or another model architecture when
  selecting an audition model. Preferences use an available match and fall back
  to the selected model; a manual choice can override the preference.
- Use doubling to select a second capture inside a NAM host, with Stereo and
  Switch modes and the secondary controls advertised by the device.
- Honor firmware-controlled disabled settings, re-read the resulting state after
  loading captures and request Lite when a plan exceeds two A2 captures.

### Verified resource limits

Firmware 5.2.0 exposes **two independent NAM hosts**, supporting up to **two
NAM2 / A2 Full captures or four NAM2 / A2 Lite captures** through doubling.
Lite is a processing mode for the same A2 model file. Routing and other blocks
can require Lite even below those maxima. A1 retains its single-capture
restriction.

Attempts to force three or four Full captures, a fifth Lite capture or a third
independent NAM host did not establish additional processing capacity. A write
to a disabled Full/Lite flag does not prove that the DSP runs another Full
capture. This release does not offer a verified limit bypass. See the
[firmware compatibility record](../HEADRUSH-5.2.0.md) for the observations and
remaining audio-test limits.

## Firmware 5.2.0 controls and sign-in

- Expose input calibration and the Raw, Calibrated and Normalize output modes
  when reflected by the connected NAM host and supported by its capture.
- Translate saved legacy Normalize settings to firmware 5.2's Output Mode while
  retaining the legacy path when the device still advertises it.
- Offer Tone3000 browser sign-in when the device advertises the new login method.
  The returned HTTPS address is restricted to Tone3000 domains; older devices
  keep the on-device sign-in flow. The new response path has simulated test
  coverage; the investigated hardware was already signed in.

Firmware DSP fixes are supplied by the HeadRush update. RushLink uses the
available device controls; it does not install firmware or independently verify
every change described in the vendor's release notes.

## Early-alpha and platform limits

Back up important rigs before testing writes to a device. Automated browser and
simulated-device checks do not establish audio fidelity, sustained DSP behavior
or physical-device support on every platform. The browser demo uses a simulated
session; a native build is required to communicate with a pedal.

Windows installers are unsigned; macOS builds use ad-hoc signing without Apple
notarization and can trigger Gatekeeper warnings. Linux and mobile packages are
previews. Android APKs use a local debug signing key and are not store releases.
The unsigned iPhone/iPad IPA is not directly installable and cannot be uploaded
to TestFlight without Apple signing and provisioning. The simulator ZIP requires
an ARM64 Mac and an installed iOS Simulator runtime. Neither Android emulator
checks nor iPhone/iPad simulator checks establish live HeadRush discovery,
Wi-Fi saving, audio or MIDI behavior on physical mobile devices.

## Build provenance

The published app version remains **0.1.3**, targeting **HeadRush 5.2.0**. The
released application source is the immutable `rushlink-v0.1.3` tag (`271a1e5`).
Windows packages retain the existing GitHub Actions desktop-release build;
macOS, Linux and iPhone/iPad packages follow their dedicated platform Actions
workflows at that same released tag. Android uses the validated local Windows
Android toolchain, with application-source equality checked against the tag.

Adding the firmware label to an existing package's download filename does not
change its binary contents. Platform build revisions and Actions runs accompany
the release verification record. Packaging follow-ups do not move or replace
the released tag; the source-download manifest distinguishes its exported
snapshot from the released application-source revision. See the
[release guide](../RELEASE.md) for the checks and publication procedure.

Report issues with the app version, HeadRush model, full firmware version and
steps to reproduce. Review diagnostics before sharing them. Contributions and
verified compatibility reports are welcome in the
[RushLink GitHub repository](https://github.com/Rush-Link/RushLink-App).
